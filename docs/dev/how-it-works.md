# How it works

Stock Wine and Proton run the DP4a (dot-product instruction) fallback of XeSS instead of the XMX (Intel's matrix hardware) path. The XMX path requires two components that do not exist on Linux:

* Intel's D3D12 extension library (`igdext64.dll` and its `_INTC_D3D12_*` entry points).
* A C-for-Metal (CM, Intel's GPU kernel language) compiler and runtime in the driver.

This project provides both components without modifying Proton or vkd3d-proton (Proton's D3D12-to-Vulkan translator):

* `igdext64.dll`, a shim (translation library) built on Intel's open-source [dxvk-igdext](https://github.com/GameTechDev/dxvk-igdext), answers XeSS driver queries like an Intel Windows driver and replaces every CM kernel XeSS submits with a placeholder compute shader.
* A patched Mesa ANV (Intel's Linux Vulkan driver), or `VK_LAYER_XESS_xmx` on an unpatched Mesa ANV, compiles those kernels with Intel's Graphics Compiler (`IGC`) on first use and runs them in place of the placeholders inside the normal vkd3d-proton Vulkan queue.
* `ControlLib.dll`, a stand-in for Intel's Control Library, gives XeSS frame generation the multiplier override (`XESS_FG=<n>`) that Intel Graphics Software sets on Windows.
* `amd_fidelityfx_upscaler_dx12.dll`, `amd_fidelityfx_framegeneration_dx12.dll`, and `dxgi.dll` translate AMD FidelityFX Super Resolution (FSR) 3.1+ upscaling and frame generation calls into XeSS (`FSR=xess`, `FSR_FG=xess`, `FSR_FG=inject`), or generate motion vectors from optical flow for any D3D12 game (`OFLOW_FG=1`).
* `libxess_dx11.dll` bridges D3D11 XeSS calls to D3D12 XeSS (`XESS=latest`).
* `vulkan-1.dll` adds the Intel driver interfaces that Vulkan XeSS looks for (`XESS=latest`).

## 1. The shim (`igdext64.dll`)

XeSS (`libxess.dll`) and XeSS frame generation (`libxess_fg.dll`) load `igdext64.dll` from the Wine prefix's `driverstore/filerepository/igd_faux.inf_1` folder. They call `GetSupportedVersions`, `CreateDeviceExtensionContext`, `CheckFeatureSupport`, and `CreateComputePipelineState`.

The shim does two things:

* Detects the GPU (which Wine lists under `HKLM\System\CurrentControlSet\Enum\PCI`) and reports its properties as the Windows driver would: graphics IP version, XMX support, and whether the GPU is SIMD16-native (16-wide execution; see [section 4](#4-which-kernel-variant-xess-picks)).
* Intercepts every CM kernel that XeSS submits (delivered as SPIR-V intermediate shader bytecode plus build options), writes the bytecode and options to `C:\igdext_kernels\<hash>.spv` and `.opt` (where `<hash>` is the 16-hex-digit FNV-1a hash of the SPIR-V plus options), and returns a placeholder D3D12 compute pipeline to XeSS.

### Placeholder format

A placeholder is a small DXBC (DirectX bytecode) compute shader with thread group size `numthreads(1, 1, 23)`—a prime number no game is known to use. It contains a single `store_raw` instruction that writes the magic value `0x584D5843` and the kernel's 64-bit hash as two 32-bit dwords.

The shim keeps an `fxc`-compiled template of this shader in `shim/src/dll/placeholders.inc` (generated by `tools/gen_placeholders.py`). For each kernel, the shim copies the template, patches in the hash, and recomputes the DXBC checksum (an MD5 hash with DXBC's custom end-of-message layout, implemented in `shim/src/dll/DxbcChecksum.h`). The Vulkan driver or layer then reads the hash back from the shader's constants.

vkd3d-proton does not verify the DXBC checksum (neither its own DXBC parser up to 2.14 nor `dxbc-spirv`, which 3.x uses). It keys its internal shader caches by a hash of the whole DXBC blob and preserves the three values as 32-bit constants: one vector store in vkd3d-proton 3.x, or one store per dword in 2.x. `tools/check_placeholders.py` checks that the templates (shape, magic value, checksum, hash offsets) and the shim's self-test values match the driver patch.

Older versions of the shim numbered the kernels sequentially (`map.txt`, `dyn_<id>.spv`, encoding the id in `numthreads` on the planes `z = 7, 11, 13`). Both the patched driver and the Vulkan layer still accept those id placeholders.

### Why the shim lives in each prefix

XeSS can locate `igdext64.dll` in an arbitrary folder via the `INTC_ALT_DRIVER_EXTENSIONS_PATH` environment variable, which would avoid copying the DLL into every Wine prefix. However, GE-Proton hardcodes `INTC_ALT_DRIVER_EXTENSIONS_PATH` to `C:\Windows\System32` for every game, so the per-prefix copies are still required. `install.sh` also sets `INTC_ALT_DRIVER_EXTENSIONS_PATH` to the prefix's `driverstore` folder for Proton versions that do not create a driver store at all (such as Proton 11.0), where XeSS would otherwise never find the folder on its own.

## 2. The patched driver (`patches/`)

The patched Mesa ANV driver (`patches/0001-anv-cm-kernel-injection.patch`) inspects every compute shader it compiles. A shader is recognised as a placeholder only if it has both the placeholder workgroup size (`1, 1, 23`, or the `z = 7, 11, 13` planes of older shims) and stores the magic value `0x584D5843`. Any other shader—even one with the same workgroup size—compiles normally through Mesa's `Jay` or `brw` compiler backends. Placeholders are intercepted before reaching `Jay` or `brw`.

When the driver sees a placeholder, it runs four steps:

1. **Reads the kernel hash** from the two constants next to the magic value. Because vkd3d-proton and NIR (Mesa's internal shader representation) can reorder the constants depending on the store path, the driver checks both orders and picks the pair that matches a `.spv` file in `C:\igdext_kernels` or an existing cache entry. It then looks up `~/.cache/xess-xmx/kernels/<hash>_<pci id>_<toolchain>.cmk`. The `<toolchain>` string hashes the compiler filenames in `igc/`, the contents of the compile scripts, and the packer version, so updating the compiler, scripts, or `.cmk` format triggers a clean recompile.
2. **Compiles on cache miss** by running `tools/cm-compile.sh`. This script invokes `ocloc` (the offline compiler from Intel's compute-runtime, paired with **IGC 2.10.10**, downloaded into `igc/` by `tools/get-igc.sh`) with `-vc-codegen` plus the options XeSS passed (`-doubleGRF`, `-ze-exp-register-file-size`), writing output to a temporary folder. The driver passes the GPU's PCI id and GRF (general register file) size to the script, and then packs the resulting Intel `zebin` binary into a `.cmk` file itself using a built-in C port of `tools/cmk_pack.py` (which produces byte-for-byte identical output). Aside from `ocloc`, the script starts no external programs. For older drivers that do not pack `.cmk` files in C, `tools/cm-compile.sh` falls back to `tools/cmk_pack.py`. Moving the packer into the driver cut per-kernel overhead from 0.2–0.3 s: Wuthering Waves' 90 kernels take 65–70 s in total at first launch, with about 31 s spent inside `ocloc` itself. Kernels compile one after another inside `vkCreateComputePipelines`.
3. **Replaces the shader** with the native binary from the `.cmk` file. The `.cmk` contains the GPU machine code (ISA), GRF register count, shared local memory (SLM) size, barrier and sampler flags, the compute walker payload layout (cross-thread data such as `local_size` and `group_count`, plus per-thread packed local IDs with a stride of one GRF), and the mapping from kernel surfaces to D3D12 descriptor tables.
4. **Skips the Vulkan pipeline cache** (`no_cache` flag on the shader), so a changed kernel or a retry after a failed compile is always picked up on the next launch.

### Large GRF Mode on Xe-HPG and Xe2

CM kernels use either 128 or 256 registers per thread, specified in their compile options. On Xe3, the register count is written directly into each dispatch's interface descriptor.

Xe-HPG (Alchemist) and Xe2 (Battlemage) instead use a single engine-wide hardware switch called Large GRF Mode, which stock Mesa never turns on. Without it, the first 256-register kernel hangs and resets the GPU engine. `patches/0003-anv-cm-xe2-large-grf.patch` (contributed in #16 for Xe2, extended to Xe-HPG in #31 and #32, and in #39) switches Large GRF Mode on before a 256-register CM kernel and switches it off before any other compute work (including Mesa's internal BLORP copies and clears, ray tracing `trace_rays` calls, driver-internal shaders, and indirect generated commands) and at the end of each command buffer, emitting state changes only when the mode flips. It also drops CM dispatches with a zero workgroup count (which the Vulkan specification defines as a no-op) on all GPU generations.

### Resource binding at dispatch

At each dispatch, ANV builds the kernel's surface binding table directly from vkd3d-proton's descriptor heap. XeSS root signatures use one D3D12 descriptor table per resource, and vkd3d-proton passes the heap offsets in Vulkan push constants. ANV reads the sampler state from the root signature's static sampler (stored as an immutable sampler in the Vulkan pipeline layout) and programs the hardware SLM and barrier fields. Everything stays inside the normal Vulkan queue.

Kernels whose sampler is passed in a descriptor table rather than as a static sampler—used by the FSR 4 on XMX plugin ([docs/games.md](../games.md#fsr-4-on-xmx-upscaler-builds-from-the-optiscaler-discord))—place that sampler table as the last root parameter after the surfaces. `patches/0005-anv-cm-sampler-descriptor-table.patch` handles this: because vkd3d-proton puts one push-constant dword per descriptor table at the end of the push constants, the surface tables end one dword earlier, and ANV copies the sampler state from vkd3d-proton's sampler heap. XeSS itself uses static samplers and does not take this path.

Because this binding code reads vkd3d-proton's classic descriptor heap, `install.sh` sets `VKD3D_DISABLE_EXTENSIONS=VK_EXT_descriptor_buffer,VK_KHR_present_wait2` (disabling `VK_KHR_present_wait2` avoids a crash in `vkWaitForPresent2KHR` when frame generation presents multiple frames per rendered frame). If the driver cannot find a vkd3d-style descriptor heap, it logs `no vkd3d-style descriptor heap` and leaves the kernel as a no-op.

### Failed compiles

If a kernel fails to compile, the driver records its hash in `C:\igdext_kernels\compile_failed.txt`. While that file exists, the shim declines the Intel extension context on subsequent launches, so XeSS falls back to its generic DP4a path rather than rendering corrupted output.

At the next game launch, when the Vulkan device is created, the driver retries compiling the listed kernels once and deletes `compile_failed.txt` if they all succeed. If a kernel fails a second time, the driver stops retrying until one of the following happens:

* A graphics component is newer than `compile_failed.txt` (the compiler in `igc/`, `tools/cm-compile.sh`, the patched driver, or the system's Mesa).
* The game's `libxess.dll` or `libxess_fg.dll` is newer than `compile_failed.txt` (for example after a game update; the shim deletes the marker).
* You delete `compile_failed.txt` manually or re-run `install.sh`.

### Self-test (`anv_canary`)

Before the shim accepts an extension context, it creates one extra test compute pipeline on the game's D3D12 device (`shim/src/dll/placeholders.inc`, second template). It uses workgroup size `(1, 1, 19)`, the magic value `0x584D5843`, and two specific test constants in place of the kernel hash. Interpreted as 32-bit floats, those two constants are a denormal number and a signaling NaN (not-a-number), so if any translation layer flushes denormals to zero or canonicalizes NaNs, the test catches it.

When the patched driver (or the Vulkan layer) sees `(1, 1, 19)` with the magic value and both exact test constants, it writes the file `C:\igdext_kernels\anv_canary`. (Drivers from older releases of this package only know the older `(1, 1, 17)` self-test shape, so a new shim paired with an old driver fails the self-test and falls back to DP4a instead of producing noise; current drivers still answer `(1, 1, 17)` for older shims.)

The shim accepts the extension context only if `anv_canary` has a timestamp newer than the start of the game process. Otherwise, it declines the context and XeSS runs as on a system without the Intel extension: DP4a super resolution and generic frame generation (capped at 2x). Declining the context is used instead of reporting `LSCSupported=0`, because `LSCSupported=0` would disable XeSS frame generation completely. This self-test catches any case where placeholders would otherwise execute as no-ops: the stock driver running without the layer, environment variables not reaching the game, or a vkd3d-proton update changing how compute shaders reach the driver.

## 3. The Vulkan layer (`layer/`)

`VK_LAYER_XESS_xmx` (`layer/libVkLayer_xess_xmx.so`) runs the same XMX kernels on an **unpatched** Mesa ANV driver from outside the driver, on **Xe3** GPUs. On Xe3, `install.sh` uses the package's unpatched Mesa 26.3 (`lib/mesa-stock-26.3.0/`) with this layer for the entire session, and `xmx-stock.sh` uses the layer with the Linux distribution's own `vulkan-intel` package for a single game.

On Xe-HPG and Xe2 (or with `XMX_DRIVER=patched`), the session uses the patched driver for D3D12 games because 256-register kernels on those GPUs require Large GRF Mode, which only the driver can switch (`patches/0003`). When the layer is loaded alongside the patched driver, it only intercepts XeSS's native Vulkan path (`vkwrap/`, [section 7](#7-the-vulkan-wrapper-vkwrap)); the patched driver's serialized shader binaries have a longer `prog_data` structure (`pd_size_patched` in `layer/src/layouts.h`), and the patched driver injects D3D12 kernels itself.

### Layer pipeline injection

1. **Placeholder detection (`layer/src/placeholder.c`):** The layer intercepts `vkCreateComputePipelines` and scans the incoming SPIR-V from vkd3d-proton for the shim's placeholder compute shaders (both hash placeholders and older id placeholders).
2. **Compilation:** On a match, the layer calls `tools/cm-compile.sh` with `CM_NO_LOAD_PAYLOAD=1` (telling the compiler that the kernel receives its payload in registers rather than loading it from memory). Compiled layer kernels are cached as `~/.cache/xess-xmx/kernels/*.cml` and hashed with BLAKE3.
3. **Register prologue (`layer/src/prologue_table.inc`):** The layer prepends a short machine-code prologue to the compiled kernel to load the payload into registers. This prologue is assembled from a precomputed table of instruction encodings generated by `tools/gen_prologue_table.py`, so the layer does not need an assembler at runtime.
4. **Pipeline binary wrapping (`layer/src/anvbin.c`, `layer/src/template.comp`):** The layer wraps the prologue+kernel binary into ANV's internal serialized shader format, using a template shader compiled by the running ANV driver as a base. It then creates the real Vulkan compute pipeline via `VK_KHR_pipeline_binary`, using vkd3d-proton's pipeline layout plus one extra descriptor set owned by the layer.
5. **Surface binding at dispatch:** When the game dispatches a replaced pipeline, the layer copies the kernel's surface descriptors from vkd3d-proton's descriptor heap into the layer's extra descriptor set and binds it.
6. **Self-test:** The layer answers the shim's `anv_canary` self-test only after its own check on the Vulkan device passes. If the running Mesa version is not in the layer's layout table, the layer does not write `anv_canary`, the shim declines the extension context, and XeSS falls back to DP4a.

Because ANV's internal serialized shader layout changes across Mesa versions, `layer/src/layouts.h` carries one offset table per supported version: Mesa **26.1**, **26.3**, and **27.0-devel**. These offsets were measured empirically with `layer/tests/layout_probe.py` on binaries exported from the test shaders in `layer/tests/variants`, not copied from Mesa's source code.

## 4. Which kernel variant XeSS picks

When XeSS calls `CheckFeatureSupport(OPTIONS2)`, it asks for three booleans—`SIMD16Required`, `LSCSupported`, and `LegacyTranslationRequired`—and selects one of three kernel sets based on the answer:

* **`SIMD16Required=0`, `LSCSupported=1` (Xe-HPG set):** SIMD8 kernels that read and write images using legacy `gather4.typed` and `scatter4.typed` sampler/data-port messages. The shim reports this on Xe-HPG (Alchemist), which is the hardware these kernels were built for. Xe2 and Xe3 hardware and IGC do not support those legacy messages; a hand-rewritten version of this set on Xe3 left a stippled ghost trail behind moving objects, and `libxess_fg.dll` with `SIMD16Required=0` requests kernels that fail to compile on Xe2/Xe3.
* **`SIMD16Required=1`, `LSCSupported=1` (Xe2/Xe3 set):** A separate SIMD16 kernel set (57 of Wuthering Waves' 90 kernels differ from the SIMD8 set) that uses `lsc.load.quad.typed` and `lsc.store.quad.typed` Load/Store Cache messages. These compile unmodified for Xe2 and Xe3, and the shim reports this on Xe2 and Xe3.
* **`LSCSupported=0`:** No CM kernels are submitted; XeSS runs its generic DP4a HLSL shaders.

### XeSS frame generation (`libxess_fg.dll`) and `XESS_FG`

XeSS frame generation (`libxess_fg.dll`) uses the same extension interface. It opens four API-version-10 extension contexts (plus one API-version-11 context that creates no pipelines) and compiles its own CM network. In Wuthering Waves, 60 of the 90 total CM kernels belong to `libxess_fg.dll`; half of them execute `dpas` (Dot Product Accumulate Systolic, the XMX hardware matrix instruction), and at 4x frame generation twelve of them run once per generated frame. OptiScaler-driven XeFG in Forza Horizon 6 compiles an additional 24 CM kernels on XMX. Running with `IGDEXT_TRACE=1` logs the calling DLL for every context, feature query, and pipeline, distinguishing super resolution (`libxess.dll`) from frame generation (`libxess_fg.dll`).

#### Frame multiplier override (`ControlLib.dll` and `XESS_FG`)

On Windows, Intel Graphics Software can override how many frames XeSS frame generation produces. When a game creates its frame generation context, `libxess_fg.dll` loads `ControlLib.dll` from `C:\Windows\System32`, queries the 3D feature "frame generation" globally and for the current executable, and uses the returned value as the maximum number of interpolated frames instead of the game's menu setting.

Because Wine has no `ControlLib.dll`, `install.sh` places `controllib/ControlLib.c` (compiled to `ControlLib.dll`) into every prefix. It implements the exact calls `libxess_fg.dll` makes—device enumeration through DXGI and the 3D feature query—and returns the multiplier from `XESS_FG=<n>`. `libxess_fg.dll` accepts the values defined in Intel's public enum: `2`, `3`, and `4` (2x to 4x).

For values above 4x (`XESS_FG=5` through `8`, experimental), `libxess_fg.dll` ignores the `ControlLib.dll` return value. Instead, the shim (`shim/src/dll/XellHook.cpp`, which hooks `libxess_fg.dll` exports) raises the limit in memory by observation through the public API:

1. After the game creates its frame generation context (with the `ControlLib.dll` override set to 4x, which means 3 interpolated frames), the shim scans `libxess_fg.dll`'s writable data sections and records the addresses of every 32-bit integer equal to `3`.
2. The shim creates a temporary probe context with the `ControlLib.dll` override set to 3x (2 interpolated frames) and filters its address list down to the single 32-bit value that changed from `3` to `2`.
3. It writes the target interpolated frame count (`XESS_FG - 1`) to that address and calls the public function `xefgSwapChainGetProperties` on the game's context to verify that `libxess_fg.dll` now reports the new maximum. If the check fails or more than one address matched, the shim restores the original value and leaves the game at 4x.

This probe runs before the game sizes or initializes frame generation (either immediately inside context creation, or on the next call if `libxess_fg.dll` loaded `igdext64.dll` mid-creation). If a game also calls `xefgSwapChainSetNumInterpolatedFrames` at runtime (such as Wuthering Waves when changing its 2x/3x/4x menu), the shim's hook replaces the argument with `XESS_FG - 1`.

## 5. XeLL (Intel Low Latency)

Games with XeSS frame generation also load Intel's low-latency library, `libxell.dll`.

### Why driver mode does not start under Proton

On Windows, XeLL has a driver mode that reads CPU and GPU render-submission timestamps from the Intel driver through four undocumented extension entry points and a shared timing buffer.

Under Wine/Proton, `libxell.dll` runs in its cross-vendor fallback mode (logging `[XeLL] Using built-in context`), where it paces frames using application-side timestamps. The reason is in `libxell.dll` itself (read from 1.3.2.10, the SDK copy; `shim/src/dll/XellDriver.cpp`):

1. Before loading any extension DLL, `libxell.dll` calls `GetProcAddress(GetModuleHandle("ntdll.dll"), "wine_get_version")`. If that function exists, `libxell.dll` immediately selects its built-in cross-vendor context and never loads `igdext64.dll`.
2. Even when `wine_get_version` is hidden from `libxell.dll`, it requests extension interface version `5/13` or `4/13`, checks that the driver version string is at least `31.0.101.6252`, and checks that `GTGeneration` equals one of Intel's internal `PRODUCT_FAMILY` IDs (`1300` for Panther Lake, `1275` for Lunar Lake, `1274` for Battlemage, `1270` for Alchemist; the shim normally reports `30` in `GTGeneration`).

`IGDEXT_XELL_PROBE=<version>` and `tools/xell-probe.sh` ([docs/dev/debugging.md](debugging.md#xell-driver-mode-probe)) hook `GetProcAddress` in `libxell.dll` to hide `wine_get_version` and report the product family ID so developers can inspect the undocumented timing buffer accesses. Even with the probe enabled, Wuthering Waves stays in the built-in context.

### Wuthering Waves 30 fps frame-cap fix

Right after enabling frame generation, Wuthering Waves passes a 33.3 ms frame cap (30 fps) to XeLL, locking the game to 30 fps until the player opens and closes the pause menu. In `shim/src/dll/XellHook.cpp`, if a frame cap arrives within 1.5 seconds of frame generation being enabled, the shim replaces it with the previous cap value. By default this runs only for Wuthering Waves (`IGDEXT_XELL_FIXCAP=1` enables it for any game; `IGDEXT_XELL_KEEPCAP=1` disables it).

### Queue-draining low latency mode

XeLL's built-in cross-vendor context only sleeps to enforce a frame rate cap. Its internal estimate of CPU frame time includes the time spent waiting in the GPU/present queue, so a GPU-bound game with a full frame queue looks CPU-bound to XeLL, and `xellSleep` never waits.

To cut that queue latency, the shim (`shim/src/dll/XellHook.cpp`) adds its own wait right after `xellSleep` whenever frame generation is active (detected via `xefgSwapChainSetEnabled` or `xellSetFgEnabled`). Using the timestamps the game already hands to XeLL's frame reports, the shim waits after `xellSleep` until:

    newest finished frame in XeLL's frame reports + frames in flight x a frame's time - the lowest simulation -> render submit time of the last 64 frames

The frame time is learned before applying any wait, and only raised when the CPU simulation-to-submit time shows a queue again (such as in a heavier scene). Because the wait itself never raises the frame time, the wait cannot drift down the frame rate; it follows a lighter scene down. The wait is bounded to two frame times.

This mode applies to a game's native XeSS frame generation. On the FSR translation routes (`FSR=xess`, `FSR_FG`, `OFLOW_FG`), the package's frame generation DLL reports each present to XeLL immediately before the next frame's `xellSleep`, so the shim sees zero frames in flight and does not add a second wait. `IGDEXT_XELL_CAP=off` disables this mode; `IGDEXT_XELL_CAP=auto:<ms>` shifts the target start time by `<ms>` milliseconds.

## 6. The D3D11 bridge (`dx11bridge/`)

Intel's official D3D11 XeSS library (`libxess_dx11.dll`) contains no upscaler of its own: it forwards every call to an internal interface of the Intel Windows D3D11 driver, which does not exist under Wine/Proton.

When you launch a D3D11 game (or OptiScaler in a D3D11 game with `Dx11Upscaler=xess`) with `XESS=latest %command%`, `tools/proton-hook.py` replaces the game's `libxess_dx11.dll` with `dx11bridge/libxess_dx11.dll` and places the XeSS SDK's D3D12 `libxess.dll` next to it. The bridge implements the `xessD3D11*` API on top of D3D12 `libxess.dll`:

* For each D3D11 XeSS context, the bridge creates a companion D3D12 device (via vkd3d-proton) on the same GPU adapter as the game's D3D11 device (which runs on DXVK).
* On each frame, the bridge copies the game's D3D11 input textures into D3D11/D3D12 shared textures, converting the depth buffer into `R32_FLOAT` through a small compute shader.
* A shared D3D11/D3D12 fence orders execution across the two APIs (`D3D11 -> D3D12 -> D3D11`): D3D11 signals after copying the inputs, D3D12 waits, dispatches XeSS super resolution on XMX through the normal shim and driver path, signals the fence, and D3D11 waits before copying the shared output texture back into the game's D3D11 output texture.

The texture copies cost a small amount of memory bandwidth per frame; the XMX kernel execution is identical to a native D3D12 game.

## 7. The Vulkan wrapper (`vkwrap/`)

XeSS's native Vulkan path in `libxess.dll` runs XMX kernels only when the Vulkan driver exposes three proprietary Intel interfaces outside the standard Khronos Vulkan registry:

* A device function for binding the kernels' descriptors.
* A physical-device properties structure reporting that the Intel path is available.
* A `vkCreateShaderModule` extension structure carrying the CM kernel's build options.

Because Wine's `vulkan-1.dll` forwards only standard registry structures and functions, `libxess.dll` under stock Proton logs `Unable to initialize Intel Extensions layer. Using suboptimal implementation.` and falls back to DP4a.

When you run a Vulkan game with `XESS=latest %command%` (or add `XESS_VK=1` if the game loads `vulkan-1.dll` dynamically at runtime), `tools/proton-hook.py` places `vkwrap/vulkan-1.dll` next to the game executable.

`vkwrap/vulkan-1.dll` forwards all standard Vulkan calls to Wine's `vulkan-1.dll` (using forwarding stubs generated by `vkwrap/gen.py` from `vkwrap/exports.txt`) and implements the three Intel interfaces:

1. When `libxess.dll` creates a CM shader module, `vulkan-1.dll` writes the SPIR-V and build options to `C:\igdext_kernels\<hash>.spv` / `.opt`—the exact same folder and format as the D3D12 shim, sharing the same compiled kernel cache—and hands `libxess.dll` a placeholder shader module.
2. When `libxess.dll` records kernel descriptor bindings, `vulkan-1.dll` passes them to `VK_LAYER_XESS_xmx` (`layer/`), which replaces the placeholder compute pipelines with the compiled XMX kernels and binds their descriptors.
3. Before reporting to `libxess.dll` that the Intel Vulkan path is available, `vulkan-1.dll` runs a self-test on the game's `VkDevice` and waits for `VK_LAYER_XESS_xmx` to answer it. If the layer is not active (or on Xe-HPG and Xe2, which the layer does not support), the self-test fails and `libxess.dll` stays on DP4a.

Note that `libxess.dll` itself disables the Intel Vulkan path whenever the Khronos validation layer is loaded.

## 8. FSR on XeSS internals (`ffxfg/`)

The DLLs in `ffxfg/` implement AMD's FidelityFX API (`amd_fidelityfx_upscaler_dx12.dll` and `amd_fidelityfx_framegeneration_dx12.dll`) on top of Intel's `libxess.dll`, `libxess_fg.dll`, and `libxell.dll`.

### Upscaling (`ffxfg/ffx_xess.cpp`)

When the game creates an FSR upscaling context, `amd_fidelityfx_upscaler_dx12.dll` creates an XeSS super resolution context on the same D3D12 device.

* **Version reporting:** The DLL reports both FSR `4.0.2` and FSR `3.1.5` in version queries so games that check for a specific FSR 3.1+ or FSR 4 provider version offer the option in their menus.
* **Initialization and quality mapping:** XeSS is initialized on the first upscale dispatch (and re-initialized if the output resolution changes). The DLL picks the XeSS quality preset whose optimal input resolution covers the game's maximum render resolution (for example, FSR Quality at 1.5x maps to XeSS Ultra Quality at 1.5x); XeSS accepts any per-frame render resolution within that preset's scaling range. When the game queries render resolution, jitter sequence, or quality ratios, the DLL returns FSR 3.1's exact numbers so the game's rendering pipeline behaves identically to native FSR.
* **Flags and resource states:** FFX context and dispatch flags are mapped to their XeSS equivalents: inverted depth, display-resolution motion vectors, jittered motion vectors, auto-exposure, or an external exposure texture. If the game does not set the FFX HDR flag, XeSS is configured for LDR input. Motion vector scale factors are passed straight to XeSS (both APIs multiply motion vectors by the scale to get pixel offsets). Around the dispatch, the DLL moves the input resources to the states XeSS reads them in and back afterward.

For games shipping FSR 3.1.0 to 3.1.3—where upscaling and frame generation live inside a single `amd_fidelityfx_dx12.dll`—`tools/proton-hook.py` replaces that file with AMD's signed `amd_fidelityfx_loader_dx12.dll` from FSR SDK 2.4.0 (`ffx/`, downloaded by `tools/get-ffx.sh`), which exports the same five entry points and loads `amd_fidelityfx_upscaler_dx12.dll` and `amd_fidelityfx_framegeneration_dx12.dll` from its directory.

### Frame generation (`ffxfg/ffx_xefg.cpp`)

An FSR 3.1+ game creates two FidelityFX frame generation contexts, which `amd_fidelityfx_framegeneration_dx12.dll` maps onto XeSS-FG (`libxess_fg.dll`) and XeLL (`libxell.dll`):

* **Swap chain context** (FFX's `WRAP`, `NEW`, or `FOR_HWND` creation variants): Replaced by an XeSS-FG proxy swap chain paired with an XeLL context (which XeSS-FG requires). The game receives a thin wrapper around the XeSS-FG proxy that adds the XeLL present markers and the present ID.
* **Frame generation context:** On each frame's FFX prepare call, the DLL tags the depth, motion vectors, jitter, and camera for XeSS-FG, with view and projection matrices built from the camera vectors. By default, the DLL copies depth and motion vectors during the prepare call so the game cannot overwrite them before `Present` (`FFX_XEFG_VALIDITY=0` tags them as valid until the next present instead of copying, to measure what the copy costs). If the game passes a HUD-less color texture in the FFX configure call, the DLL passes it as XeSS-FG's UI composition input (`FFX_XEFG_HUDLESS=0` disables this). When the game dispatches the FFX frame interpolation command list, the DLL does nothing, because XeSS-FG performs its interpolation inside the proxy swap chain.

#### Early swap chain setup and cached depth flags

Games create the FFX swap chain context at startup, *before* creating the FFX frame generation context that specifies how the game's depth buffer is stored. Because XeSS-FG is set up at swap chain creation time, the DLL uses the flags the game gave the last time (kept per executable in `%LOCALAPPDATA%\ffx_xefg\`), or assumes inverted depth on the first run. If the flags the game later passes to the frame generation context differ from what was used at swap chain creation, `ffx_xefg.log` logs `wrong until the game starts again`.

#### Swap chain workarounds

The wrapper handles three behaviors that otherwise break games when running on an XeSS-FG proxy swap chain:

* **Frame latency waitable object:** Games wait on the swap chain's waitable object before starting each frame. The proxy's waitable object deadlocked CONTROL Resonant within seconds, so the game gets an object of the DLL's own, released when the present returns (`FFX_XEFG_OWNWAIT=0` gives the game the proxy's object). With `FFX_XEFG_PACE=1`, the DLL releases the object when the GPU has finished the presented frame instead, as DXGI's does: after each present the game's queue signals a fence, and a thread of the DLL releases the object when the fence is reached, or after 200 ms regardless.
* **Swap chain lifetime:** AMD's FFX swap chain context holds a reference to the swap chain until the FFX context is destroyed. Wuthering Waves relies on this, releasing its own swap chain reference while continuing to present. The DLL's swap chain context holds a reference the same way.
* **Exclusive fullscreen:** XeSS-FG does not interpolate in exclusive fullscreen. A request for it is answered as if it had worked while keeping the swap chain windowed (under gamescope it looks the same). After a mode change or a resize, interpolation is switched on again.

#### Adapter vendor spoofing (`FSR_VENDOR=amd`)

Some games (such as Wuthering Waves) hide their FSR menu unless DXVK reports an AMD GPU (`dxgi.customVendorId = 1002`). XeSS-FG and XeLL read the vendor the same way and need Intel's (XeSS SR does not). To keep both working, `amd_fidelityfx_framegeneration_dx12.dll` answers adapter queries coming from `libxess_fg.dll` and `libxell.dll`—and only theirs—with Intel's vendor ID when the adapter description is Intel's (`FFX_XEFG_VENDOR=0` turns this off), and the package's `ControlLib.dll` takes such an adapter as Intel's.

### Injecting frame generation from upscaling (`FSR_FG=inject`, `ffxfg/dxgi_xefg.cpp`)

For games that have FSR 3.1+ upscaling but no FSR frame generation (such as Forza Horizon 6, whose menu offers only NVIDIA DLSS-G), `FSR=xess FSR_FG=inject` places `dxgi.dll` and `ffx_xefg_bridge.dll` (the frame generation DLL under a name AMD's FidelityFX loader ignores) next to the upscaler in the game executable's folder.

1. `dxgi.dll` passes everything to the prefix's `dxgi.dll` and changes the two slots of the DXGI factory that create swap chains.
2. When the game creates a D3D12 swap chain, `dxgi.dll` wraps it in the same XeSS-FG proxy swap chain and wrapper as a FidelityFX swap chain context (any other swap chain stays plain, and so does a D3D12 one if XeSS-FG fails).
3. Each upscale dispatch tags that frame's depth and motion vectors under frame IDs of the DLL's own. Because a game may record a frame's upscale before it presents the frame before, presents take the upscaled frames in order, and a present without one (menus, loading) is not interpolated.

Because the game hands over neither camera vectors nor a HUD-less image or UI layer, XeSS-FG gets a fixed view with the real projection and interpolates the HUD with the rest of the image.

## 9. Optical flow frame generation internals (`OFLOW_FG=1`, `ffxfg/ffx_oflow.cpp`)

For D3D12 games that have neither XeSS nor FSR 3.1+ (`OFLOW_FG=1`), the package works out motion vectors from the final image itself:

1. **Swap chain interception:** `dxgi.dll` (the same one as `FSR_FG=inject`) gives the game an XeSS-FG swap chain.
2. **Optical flow estimation:** FidelityFX optical flow (from FidelityFX SDK 1.1.4, MIT license, linked statically into `ffxfg/amd_fidelityfx_framegeneration_dx12.dll`) estimates, for every 8x8 block of the final image, how it moved since the last frame (or at `1/n` of the display size when `FFX_XEFG_OFLOW_DIV=n` is set).
3. **Motion vector expansion (`ffxfg/oflow_expand.hlsl`):** A small compute shader turns those block vectors into per-pixel motion vectors at display size and writes a constant depth (`1.0` by default, configurable via `FFX_XEFG_OFLOW_DEPTH`).
4. **XeSS-FG interpolation (`ffxfg/ffx_oflow.cpp`):** XeSS-FG gets those motion vectors and the constant depth with an identity camera, no jitter, and no UI texture.

### Automatic rendered-frame pacing (`FFX_XEFG_CAP=auto`)

Because generated frames sit between two rendered ones, an uneven rendered frame rate shows directly (for example, Resident Evil 4 without any limit swung between 20 and 28 ms per rendered frame). By default (`FFX_XEFG_CAP=auto`), the DLL limits the rendered frame rate through XeLL's frame cap:

* **GPU time measurement:** The GPU time of every frame is measured on the game's queue, from the game's first submission after a present to the optical flow right before the next one.
* **GPU clock scaling:** When a capped GPU idles, its clock drops and the same work takes longer; without compensation, the cap would drag itself down. To prevent this, the measured GPU time is scaled by the GPU clock read from the `xe` driver's `act_freq` in `sysfs`.
* **Target interval calculation:** The interval is that clock-scaled time (90th percentile) plus what a frame needs beyond it (the interpolation and the present, initialized to `FFX_XEFG_CAP_PAD`, `1.5` ms by default, and learned from the frames in which the GPU could not keep up), at least one display refresh per frame shown.
* **External limiter handoff:** When the game reaches an outside limit (gamescope's frame limit or the display's refresh rate) and waits in `Present`, the cap goes off and that limit paces the game, until the game no longer reaches it.

Because the game provides no XeLL markers, XeLL cannot see where the game reads its input and cannot reduce latency as it does for a game with XeSS.
